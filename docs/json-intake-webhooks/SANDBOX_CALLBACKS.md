## Scope and contract

The separate `json-intake-webhooks.yaml` stack provides its own retained DynamoDB outbox and worker. Its only existing-data access is GetItem against the sandbox receipt table and GetObject against the receipt-evidence prefix. It cannot write receipts/artwork, submit Lift orders, call Proof/Wrike/SES or use inbound intake credentials. An optional exact signing-secret ARN grants GetSecretValue only.

The accepted `pathfinder.webhook.v1` envelope, X-Pathfinder headers, raw-byte HMAC, event IDs, status revisions, retry offsets and ten-attempt/24-hour delivery cycle remain unchanged. The local loopback transport stays the default. HTTPS requires the explicit sandbox transport capability. URLs come only from trusted configuration; it validates exact destination, HTTPS/443, DNS public addresses, pinned lookup/TLS hostname, no pooling and no redirects. Receiver bodies and native errors are discarded. Dispatch's ten-second deadline covers DNS and network; late DNS completion cannot start a request. Paused/exhausted deliveries require an audited operator replay; the existing trusted replay helper now accepts the explicit HTTPS capability while preserving default loopback restrictions. No public replay route exists.

This first activation permits `order.received` and existing allowlisted customer artwork findings only. It refuses receipt histories containing confirmation/shipping evidence until the authoritative Lift source integration receives separate review. Shipping events remain required for launch and retain their existing local tests; they are not activated by this candidate. Line-bound customer findings PDF_RGB_PROFILE_MISSING and PDF_COLOR_REVIEW_REQUIRED receive fixed-text review callbacks. They ask for production review and preservation of the original, never automatic profile assignment or color conversion. Internal findings remain excluded.

Received events retain the existing relative authenticated `status_url`; receivers resolve it against the supplied sandbox intake base, not their callback origin. Delivery visibility is the safe IAM worker invocation result (event/state/attempt counts/retry time/support flag), not a change to the partner status API.

## History, recovery and limits

Trusted configuration must explicitly name 1–20 receipt IDs. There is no customer-wide scan or implicit historic backfill. Enabling a receipt deliberately queues its original received event plus eligible historic findings; stale findings are rechecked and suppressed before send. A removed receipt cannot be dispatched. Re-adding it retains prior delivered/paused history rather than generating a new identity. Choose the four existing test receipts only after reviewing this backfill behavior with the receiver.

Each run reads complete immutable history through a captured latest revision, checking scope, identity and checksums before materialization. Limits: 250 maximum revision number per receipt, 500 total revisions, 16 MiB aggregate history and remaining-time checks. New commits after the snapshot are recovered next run. Repeated materialization converges on deterministic event IDs. Atomic latest/audit transactions prevent duplicate claims and preserve attempt/replay history; stale CAS cannot overwrite delivery. A crash around enqueue is recoverable; a crash around HTTP is uncertain and retries the same event under the accepted receiver deduplication contract. Durable outbox records are bounded to 350 KiB. There is no TTL/pruning of receipt history or outbox audit in this test slice.

Retry offsets are earliest eligible times, not exact scheduled delivery times: a one-minute retry can wait for the next two-minute tick. The strict 24-hour deadline takes precedence over the maximum ten attempts. The nominal tenth attempt is at the deadline and is skipped if the scheduler arrives even slightly late; this existing contract behavior is preserved and tested, not silently extended.

Each run attempts at most ten due events, uses a 120-second/512 MiB worker with reserved concurrency one, and stops starting deliveries with under twenty seconds left. Three independent settings default false: Enabled (queue/status work), DeliveryEnabled (external HTTP), ScheduleEnabled (two-minute invocation). A disabled worker exits without reading configuration, receipts or secrets. A queue-only run reads no signing secret and sends nothing.
