## Durable events and ownership

The materializer reads every immutable receipt revision. Stable event IDs include integration scope and committed source identity; the serialized body and its hash never change. Deterministic inserts serve as the recovery cursor: a crash before or after insertion is recovered by rescanning. Concurrent scans converge on the same event. No receipt history pruning is supported. A production implementation needs transactional storage, bounded indexing/scanning, retention and operational recovery.

`order.received` comes from revision zero. `order.action_required` comes only from an allowlisted, validated line-bound customer finding, with fixed safe text. Generic shared manual review, internal failures, URL renewals, claims and asset checkpoints do not create customer-action notifications. Pending action events are checked against current findings before each send; resolved or changed findings suppress the old event. Status retains resolved issue history. The source check and HTTP are separate operations: receivers must still tolerate later resolution and out-of-order events and consult authenticated status.

`order.confirmed` requires a confirmed shared Intake Assurance record plus matching customer/integration/receipt/source-order/EXT_ID/job/submission/target-customer/target-order and verified-association evidence. Evidence and shared state are read twice, drift fails closed, and receipt CAS stores the immutable association hash. Asset success or webhook HTTP success cannot confirm an order. The evidence loader is an injected, read-only test projection; actual authoritative job/submit store binding and transactional consistency are deferred to the Lift slice. No job or submission is created here.

## Delivery and receiver contract

The implementation preserves the sent `pathfinder.webhook.v1` draft and its exact 441-byte synthetic HMAC vector. HMAC-SHA256 uses UTF-8 secret bytes and `timestamp + "." + exact raw body`, with the documented event ID, key ID, timestamp, signature and attempt headers. Signing keys are resolved independently of intake credentials and never persisted. Key rotation changes headers without rewriting the body. Receiver verification authenticates raw bytes before parsing, accepts a five-minute timestamp window, binds header/body ID and expected test store, and permits unknown event types. The local inbox durably deduplicates event IDs and detects changed-body reuse; its retention is indefinite. Application handlers must implement their own durable revision-aware processing after inbox acceptance; the ordering test demonstrates the rule, not a production consumer.

Outbox revisions use fsync and atomic exclusive publication, with cross-process CAS. Claims precede HTTP and last 15 seconds; sends time out within 10 seconds. A dead worker's outcome is recorded as uncertain before retry. Late acknowledgements cannot overwrite a newer claim. Existing uncertain Lift/Wrike semantics are unchanged.

Ten total attempts use the sent offsets of 0, 1, 5, 15, 60, 180, 360, 720, 1080 and 1440 minutes from the first attempt, within 24 hours. Any 2xx acknowledges; 408, 425, 429, 5xx, network failure or timeout can retry. Retry-After is a lower bound inside the same window; exceeding it exhausts delivery. Redirects are never followed. Other statuses pause; 401/403/404/410 require endpoint attention. Safe status includes attempt counts, next attempt, pause/exhaustion and support-action flags. Receiver response bodies and network error text are discarded. No external incident, email or support alert is sent.

Trusted configuration binds customer/integration/store/test environment, endpoint ID/revision and destination hash. Payloads cannot choose destinations. A config/destination mismatch pauses delivery. Only explicit `http://127.0.0.1:<port>` test receivers are implemented. This local HTTP exception does not satisfy or replace the draft's production HTTPS requirement. External delivery remains impossible through the supplied transport. A production transport requires separate reviewed HTTPS/DNS/SSRF, destination registration and credential bindings.

Controlled replay is a trusted local function, with no partner/admin HTTP route. It requires paused/exhausted state and records operator, request ID, reason, time, endpoint revision and destination hash. Repeating the same request is idempotent; changing its audit binding is rejected. An explicit replay starts a new capped delivery cycle, preserving the event ID, raw body and all earlier attempts. A destination change requires a new configuration revision. Source checks still apply.

## Review details and remaining gates

- Public `order_revision` is the committed receipt revision plus one, beginning at 1. Internal commits can cause gaps; receivers compare monotonically, never assume consecutive values. This changes the prior local status prototype's zero-based value; there are no deployed consumers to migrate.
- Received events currently carry a relative authenticated status URL. Confirmed events have null public status-page URL/expiry. A trusted public origin and authorized status-page association must be reviewed before partner activation; no links or grants are fabricated.
- Optional webhook status is loaded only after the existing scoped receipt lookup succeeds, under `Cache-Control: private, no-store`. Delivery records, signing secrets and destination URLs are not exposed through order input.
- Receipt confirmation fields are additive. Local outbox/inbox are new private journals; stop local drivers and preserve journals to roll back. Do not run older workers against confirmed receipts or new delivery history. There is no production data migration.
- No background materializer or delivery scheduler is installed. Local harnesses must explicitly invoke these functions. Production registration/key management, durable stores, scheduling, rate limits, retention, replay authorization and support incident integration remain release work.
- Any departure from the immutable sent draft requires versioned review. Source policy, subscriptions and shipping/hold/cancellation events remain outside this slice.
- Asset security, parser containment, packaging, manufacturing policy and all release compatibility/smoke/rollback gates in ASSET_REVIEW.md and RELEASE_COORDINATION.md remain open.
