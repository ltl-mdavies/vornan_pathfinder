# Prepaid label introduction — proposed operating procedure

Marcus approved using an order attachment as the initial delivery method for a customer-supplied prepaid label, and confirmed reuse of Momentara's existing Lift attachment mechanism. The [local delivery implementation](PREPAID_LABEL_DELIVERY.md) now retains and publishes labels for the existing `order_attachment` submission field. It is not activated in the runtime; a dispatch-entry screen/API remains outstanding.

1. **Receive and retain.** Pathfinder retains the supplied label PDF unchanged in private storage, associated with the intake receipt and confirmed Lift order. Record the retained file checksum and original source reference. A renewed download link must not silently replace the retained label with different bytes.
2. **Attach to the correct order.** Publish the retained PDF through the existing order-attachment mechanism. The initial implementation uses `PREPAID_LABEL.pdf` under a unique receipt/evidence-bound delivery path. It refuses to overwrite another attachment; adding it alongside an existing grid or to an already-created order still requires a verified append/multi-document operation. Confirm Lift/shipping staff can retrieve the attachment for the required fulfillment period.
3. **Identify the shipping instruction.** Clearly display: **Customer-supplied prepaid label — do not purchase shipping.** The attachment is an instruction/document, not evidence that the package has shipped.
4. **Check and associate before packing.** Shipping staff check the carrier/service, tracking number, destination and package suitability, then record the stable package identity and its order-line quantities. Enter tracking explicitly through the supported shipping record; do not infer it from a PDF URL. One prepaid label covers one package.
5. **Handle exceptions.** If the label cannot be used, the destination does not match, or more packages are required, hold shipping and request clarification/additional labels. Do not automatically buy replacement labels or reuse a label across packages. These exceptions are internal review until a corresponding partner notification is defined.
6. **Record actual dispatch separately.** When the package leaves, shipping staff record dispatch against that package, with operator/evidence reference and actual time where known. An unknown timestamp remains unknown. Uploading, printing or scanning a label must not establish dispatch by itself.
7. **Report the shipment.** After reviewed package data and dispatch evidence match, Pathfinder can produce the same `shipment.updated` callback used for purchased labels. The order completion callback waits for all required quantities to ship.

Before prepaid orders are activated, verify one complete example through attachment access, packing/tracking entry, dispatch and callback. Confirm the actual staff owner and supported Lift fields or external dispatch record. Initial purchased-label shipping can proceed through its separately verified source path; UPS rates are not required by this prepaid procedure.
